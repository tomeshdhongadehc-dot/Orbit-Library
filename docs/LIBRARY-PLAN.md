## 1. Goal
One website, one library. Shelves by domain: Development (now), then Deployment, Testing, Cybersecurity. Every topic keeps the Orbit format: animated lessons, quizzes, interview lab, revise, sources and proofs. The base must be standard, versioned, verifiable, private by default, and cheap to extend. Adding a shelf must never mean redoing the base.

Non-goals for v1: accounts, comments, other languages, public launch, a rewrite of existing topic content, a mobile app.

## 2. Organisation
```
Library > Shelf (domain) > Track (stack or life-cycle phase) > Topic (one Orbit page) > Lesson > Step
```
- Every topic has a manifest `topic.json`: id, title, shelf, track(s), life-cycle phase(s) (Plan, Requirements, Design, Build, Test, Deploy, Operate, Maintain), level 1 to 6, prerequisites (topic ids), tech tags, version, date, status (Draft, Verified, Audited), review-by date, counts (lessons, questions, concepts).
- Navigation is by tags, not folders. A topic can sit in two tracks.
- Lifecycle standard to cite for the phase names: ISO/IEC/IEEE 12207 (verify the exact edition and its process names before quoting).

Development shelf tracks (confirm, D3): Foundations, Languages, Frontend, Backend, Data, Architecture, Quality inside development, Engineering practice.
Existing or in progress: JS, React, Node, AWS (earlier format), API design, data modelling and indexing, caching, queues, MongoDB (finished, new format); Express, scalability, multi-tenancy, security basics (not finished).
Note: the four earlier pages (JS, React, Node, AWS) use the older build. They are listed in the library as "legacy format" and linked as they are until they are rebuilt. They do not block v1.

## 3. Scope by release
- v1 (base, private): home with shelves and tracks, topic cards (level, minutes, version, status, review-by), topic pages (existing Orbit pages unchanged), global search (data-built index), sources and proofs tab on every topic, version and date, dark and light theme, works at 375px, fully static, offline copy of every page, access gate.
- v2: progress per browser then synced accounts, bookmarks, learning paths, review of missed quiz items, "what changed" feed from changelogs, print stylesheet for cheat sheets.
- v3: fact-issue reports, community contributions by reviewed pull request, other languages, certificates.
Anything not listed under v1 is out of v1 even if easy.

## 5. Identity, versions and links
- Stable ids: `shelf/track/topic` slug, lowercase, never reused. Renaming keeps the old id as an alias and the site redirects.
- Lesson ids and quiz keys inside a topic are stable once published. Changing one needs a changelog line and a progress migration note.
- Topic version `MAJOR.MINOR`: MAJOR when a fact or an answer is corrected or a lesson is removed, MINOR for additions and wording. Each version has a date and a changelog line (format already used: `- 1.2 (2026-11-24): note`).
- Status rules: Draft (written), Verified (check scripts pass, sources and proofs filled), Audited (an independent reader re-checked a sample against original documents). Only Audited shows the green badge. Today no topic is Audited.
- Review-by date on every topic (fast-moving ones such as Node, React, cloud, MongoDB: 6 months). After that date the card says "may be out of date".
- Each topic page states the version of the thing it teaches (for example MongoDB 9.0 at research time) and the date sources were accessed.

## 6. QA strategy (what is tested, how, and the pass line)
Test levels:
1. Content checks, per topic, automated (already exist): snippet check scripts run every runnable snippet and compare the printed output; overlap check on diagrams is zero; quiz validator has zero problems; quiz answer positions balanced and not guessable; no em or en dashes; no closing script tag inside strings; every cheat id has a definition; interview ids and counts match the plan.
2. Manifest and library checks, new: every `topic.json` valid; prerequisites exist and have no cycle; ids unique; every topic has research, sources, verification, changelog; version in manifest equals version in page and changelog; every link in the library resolves.
3. Browser tests, new (Playwright): at 375, 768 and 1280 px, no horizontal scroll; every lesson opens; every quiz round starts and scores; interview and revise tabs open; proofs tab lists sources; theme toggle works; search finds known items; keyboard only path through a lesson and a quiz.
4. Accessibility (axe plus manual): focus visible, contrast in both themes, each diagram step has a text equivalent, motion respects reduced-motion. Target WCAG 2.2 AA (verify the success criteria list before claiming).
5. Performance budgets, to be set after measuring the current pages (each is about 1.2 MB today): page weight, time to first interactive on a mid phone profile, search index size. Do not invent numbers: measure first, then fix the budget in the plan.
6. Offline: open every offline file from disk with the network off: all tabs work, fonts load.
7. Regression for the engine: golden-page suite. Changing the engine rebuilds every topic and re-runs levels 1 to 4 on all of them.
8. Content audit (human): sample facts per topic against original documents. Record sample size, findings and fixes in the topic's verification file.
Known gaps today (carry into the plan, not hidden): browser test at 375px for the newest topics was run by hand and the last one (Mongo Orbit) was not run; the independent audit has not been done for any topic; some quiz distractors and a few hands-on tests are weak (listed in the audit backlog).

## 7. Release gates
A topic can be marked Verified only when levels 1, 2, 3 (375px minimum) and 6 pass and the changelog and proofs are present.
A library release needs: all topics build, no failing gate, size budget met, a rollback copy of the previous release kept, the offline folder rebuilt.
Rollback: static releases are immutable folders by version, so rolling back means pointing the host at the previous folder.

## 8. Definition of done (per topic)
Research folder (syllabus, question bank, sources with original documents first, verification, changelog) present; fact tags used and no unverified fact stated as fact; every runnable snippet executed, others labelled "illustrative, not run"; counts meet the plan; levels 1 to 3 and 6 of section 6 pass; version, date, review-by set; offline copy produced; status set honestly (Draft, Verified or Audited).

## 9. Security and privacy
- Private by default: access gate in front of the whole site. Decide the method with hosting (D6).
- Headers: Content-Security-Policy with no inline script once pages are split from the single-file build (today the pages use inline script, so v1 needs a CSP that allows it or a build step that hashes it: verify the approach), plus the standard hardening headers (verify the current recommended list from the OWASP Secure Headers project).
- No secrets in the repo, in content or in logs. Secret scanning on in CI.
- Dependencies: pin exact versions, lockfile committed, automated update pull requests, audit step in CI. The shell has very few dependencies on purpose.
- Content safety: lessons never ask readers to run unknown commands as root; every command is labelled illustrative or run. Security shelf content follows the defensive-only rule.
- Copyright: our own explanations only, links to sources, no copied document text, quote limits respected.
- v2 accounts: threat model first (what data, who can read it, row-level security tests that try to read another user's row), password and session handling delegated to the auth provider, no personal data in analytics, deletion on request.
- Privacy: if analytics is turned on, no personal data, no cross-site tracking, documented in a privacy note.

## 10. How the library itself is built (PDLC applied to our own work)
1. Plan: decisions D1 to D6 closed, scope per release fixed (section 3).
2. Requirements: each v1 feature gets 2 to 5 acceptance criteria written as checks (for example "search for 'shard key' returns the MongoDB lesson in the first 5 results").
3. Design: token file, component list, page layouts, `topic.json` schema, ADRs for each hard-to-reverse choice (hosting, search, access gate).
4. Build: small steps, each with its test.
5. Test: section 6.
6. Release: section 7.
7. Operate: link check weekly, review-by dates monitored, error reports read.
8. Maintain: changelog per topic and per library, quarterly refresh pass, deprecation note before a topic is removed.
Docs kept in repo: FORMAT, WRITER-BRIEF, PROMPT-build-an-orbit-page, this plan, ADRs.

## 11. Risks
| Risk | Likelihood | Impact | Mitigation | Owner |
|---|---|---|---|---|
| A wrong fact reaches readers | Medium | High | Fact tags, original-source priority, independent audit before green badge, review-by dates | content lead |
| Engine change breaks old topics | Medium | High | Golden-page regression suite on every engine change | engineering |
| Single-file pages grow too large | Medium | Medium | Measure, set budget, split large data into lazy-loaded files if needed | engineering |
| Private content leaks through public hosting | Low if gated | High | Access gate first, test it from a logged-out browser before any content upload | engineering |
| Writer agents drift from the format | Medium | Medium | Validators in CI, brief and format docs, per-file check scripts | content lead |
| Usage or cost limits stall large builds | Medium | Low | Build in waves, resume from saved parts | content lead |
| Source documents change after research | High over time | Medium | Version snapshot on every topic, review-by date, refresh pass | content lead |

## 12. Roadmap with exit criteria
- P0 Base: decisions closed, `topic.json` schema, tokens and component list, build script for the library shell, access gate working, CI with levels 1 to 3. Exit: a logged-out visitor sees nothing, a logged-in visitor sees the library with the four finished backend topics, all gates green.
- P1 Migrate: add every finished topic (including MongoDB) with manifests; legacy pages linked. Exit: all topics reachable from home and search, offline folder rebuilt, 375px browser test passed for each.
- P2 Development shelf: fill the tracks, audit each topic. Exit: tracks populated per section 2, each topic Verified, audit started.
- P3 Accounts and review: v2 features with a threat model. Exit: row-level security tests pass.
- P4 New shelves: Deployment, Testing, Cybersecurity with the same research, build, audit pipeline.
